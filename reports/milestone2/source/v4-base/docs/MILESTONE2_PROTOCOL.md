## 0. Overview and locked technology stack

M2A builds a tested foundation for comparing INT8 post-training quantization (PTQ) and adversarial training (AT) on PAVE's unchanged `StandardTransformerIDS`. It adds a new group-disjoint split, a frozen Experiment-C-derived training recipe, a PGD adversarial-training recipe, a frozen attack protocol with an explicit INT8 attack taxonomy, an efficiency protocol, tests, and a bounded one-seed, at-most-two-epoch pilot that touches only train and validation data. The full four-seed campaign is specified here and NOT run.

Locked stack (no dependency changes): Python 3.11.9, torch 2.5.1+cpu, numpy 1.26.4, pandas 2.2.3, scikit-learn 1.5.2 (`MinMaxScaler`), psutil 6.1.1, pytest 8.3.4. CPU only (i5-10210U, AVX2, ~8 GB RAM, ~0.8 GB free at probe time). Quantization: **PyTorch eager-mode static PTQ**, fbgemm backend, per-channel qint8 weights, quint8 activations, on the existing `research.quantization.LinearIsland` (23 `nn.Linear`). FX graph mode and PT2E fail on the unchanged model (audit §2) and are not used; `torchao` is not installed and not added.

Reuse-first rule: no second framework. New code is small, separately named modules in `research/` (list in §10) that call existing functions: `common.make_model`, `paper_described_adam.{run_epochs,build_optimizer,derived_seed,to_sequence,seed_everything}`, `attacks.attack`, `quantization.{ptq,prepare_static,inventory,load_int8,bpda_model}`, `runner.{calibration,save_quantized}`, `evaluation.{metrics,benchmark,transfer}`, `provenance.*`, `common.atomic_json`. Existing M1 modules are not edited, except one backward-compatible optional parameter on `attacks.attack` (`selector`, §J). Editing `research/`, `configs/`, `tests/` changes `provenance()["source_digest"]`; historical run roots then cannot be resumed. This is expected and never bypassed.

## A. Data protocol

**Decision A1: build ONE new split; do not reuse existing ones.** The M1 2025 stratified row split is not group-isolated (train-val 294, train-test 315, val-test 165 shared vectors; audit §5.2). The 2026 `data.partitions` split is isolated but gives 71.2/17.9/10.9 %, a validation class with 6 rows, and its test partition was partially exposed to smoke/pilot inference (audit §4.2). Neither is acceptable for M2.

**Data and mapping.** `upstream/PAVE_artifact/data/balanced_CICIoT.csv` (SHA-256 `0d869e334cc9a2795c96996fbde8fb04a8acac61f5e67c5d46aee2b0717a53ed`, 29,997x39, 27 classes, sorted label names, class id = index in `class_names` of `configs/milestone1_paper_described_adam.json`). The splitter verifies file hash, shape, finiteness and class mapping (reuse `data.build_data` checks) and fails closed.

**Grouping rule.** group id = SHA-256 of the row's 39 features as little-endian float64 bytes (`row.astype("<f8").tobytes()`, identical to `data.build_data`). Label is excluded. All rows of a group go to one partition regardless of label.

**Algorithm (`research/m2_split.py::make_split`).** Deterministic, uses labels and group sizes only, never model output.
1. Compute groups (11,953 expected) and per-group per-class counts.
2. Sort groups by (size descending, group hash ascending). Greedy initialisation assigns each group to the partition minimising the penalised objective below. The start need not be feasible.
3. Penalised objective: `V = sum_p sum_c max(0, min_{p,c} - n_{p,c})` (total shortfall below the hard minima, in rows) and `J = 4*sum_p (n_p/N - t_p)^2 + sum_p sum_c (n_{p,c}/n_c - t_p)^2 / 27`, targets `t = (0.70, 0.15, 0.15)`. Hard minima: every class has >= 20 rows in validation and in test, and >= 200 in train. Moves are compared lexicographically on `(V, J)`: a move is accepted only if it lowers `V`, or keeps `V` equal and lowers `J`. An infeasible start is therefore repaired first (V driven to 0), then J is optimised, and once V = 0 no accepted move can make it positive.
4. Local search: `numpy.random.default_rng(split_seed)`, 200,000 proposals; a proposal moves one group or swaps two groups between partitions. Stop early after 20,000 consecutive rejections.
5. **Ordered split-seed list `[20260, 20261, 20262]`**, declared in `configs/m2/data.json` before any training and never edited afterwards. `make_split` tries the seeds in order and freezes the FIRST one whose result has `V = 0` and lies inside the acceptance band. Selection uses only label counts and group sizes, never model output. Every attempt (seed, V, fractions, accepted or rejected with reason) is recorded in `split_attempts.json`. If all three fail, `make_split` raises `SplitInfeasibleError` naming the binding class and its group structure, writes `split_attempts.json` only, and reports to the user; it never drops a class or relaxes the minima silently. Only then is a documented protocol revision (new minima or a longer seed list) considered, and it is made before any training.

**Protocol revision 1 (feature-variability pin; made during FEAT-001, before any model was trained or run).** The first real run of `make_split` failed for all three declared seeds (20260, 20261, 20262) on the assertion "no constant training feature". Feature 37, `Number`, equals 10 in 29,994 of 29,997 rows. The only other values sit in three singleton rows: 8821 (9), 24213 (9) and 29510 (4). Each of those rows belongs to a class (DDoS-SynonymousIP_Flood, DoS-SYN_Flood, DDoS-ACK_Fragmentation) whose single huge duplicate group already fills the train share, so the J term pushed all of their other rows out of train; every seed put all three outside train (20260 and 20262: all in test; 20261: one in validation, two in test). The sentence "no constant training feature" in the audit (§5.4 and the scaler row) came from checking the Milestone 1 splits only; it does not hold for an arbitrary new split. The failed attempt is kept as `reports/milestone2a/split/split_attempts_infeasible_rev0.json` (status "infeasible").
Resolution chosen by the user (option A; options "waive the assertion" and "extend the seed list" were rejected). The seed list is unchanged. `V` gains a second part: `V = (row shortfall below the hard minima) + (number of at-risk features with no differing value in train)`. For each feature the modal value over distinct feature vectors is the "constant" value; a feature is at risk when at most `feature_variability.at_risk_max_minority_groups = 50` groups differ from it; it is charged one unit of V while train contains none of those minority groups. The same lexicographic `(V, J)` search repairs it. Seven features were at risk on the real data: `ece_flag_number`, `cwr_flag_number`, `Telnet`, `SMTP`, `IRC`, `IGMP`, `Number`. A feature that is constant over the whole dataset raises `DataIntegrityError`. A seed is also still rejected, and the reason recorded, if an exact post-hoc check finds any constant training feature. The rule uses feature values, labels and group sizes only; it never uses model output and does not change the targets, minima, band or seeds. It is configured in `configs/m2/data.json` (`split.feature_variability`).
Handling of `Number` in the frozen split: the singleton row 8821 (value 9) is in train, so the train range is [9, 10] and the scaler is well defined (`scale_ = 1`). Rows 24213 (value 9) and 29510 (value 4) are in validation. A value of 4 scales to -5.0, so `Number` is the dominant out-of-range feature in the held-out partitions.
**Known out-of-range risk.** The three singleton rows with `Number != 10` are an unavoidable source of out-of-range held-out features: whichever partition holds them, the train range for `Number` is at most 1 wide (or zero wide without the pin), so any row whose `Number` differs from the train extremes scales to a large excursion (here -5.0 for row 29510 in validation). Clean inputs are never clipped (§E2); the range audit lists every such row and the maximum excursion, and attack evaluation must report these rows rather than drop them. Per-class results on those rows should not be read as robustness evidence.

**Expected feasibility (exploratory, audit §5.3; to be regenerated, not trusted).** 15 groups hold 51.4 % of rows and several span three classes, so exact 70/15/15 is unreachable with all classes present. A label-count search reached about 74.8/12.6/12.6 % with all 27 classes in every partition and minimum per-class counts 38 (val/test), 678 (train). Acceptance band for the frozen split: train 0.68-0.78, validation and test each 0.10-0.17, all 27 classes in all partitions, hard minima met. The achieved counts, per-class distributions and the gap from 70/15/15 are printed in `split_report.md`. The band is not widened ad hoc; the seed-list rule above is the only fallback.

**Artifacts** (new directory `<repo>\reports\milestone2a\split\`, written once with `atomic_json`, refuses to overwrite):
- `split_m2.json`: schema version, dataset path+SHA, split seed (the frozen one), the full attempted seed list, algorithm name+version, targets, hard minima, row-ID lists (0-based CSV row index) for train/validation/test, per-partition SHA-256 of the sorted ID list, SHA-256 of the whole manifest body, per-class counts per partition, achieved fractions, group-count per partition, source digest.
- `group_manifest.json`: group hash -> (partition, row count, label counts).
- `conflicting_labels.json`: every group with >1 label (expected 229 groups, 8,697 rows): group hash, partition, per-label counts. Reported only. No relabeling, no removal. Also the per-partition count of rows in conflict groups and the resulting Bayes-style accuracy ceiling (rows in each group beyond the majority label are unavoidable errors), reported for context.
- `split_report.md` also lists, per class and per partition, the number of independent groups (distinct feature vectors) and rows, and flags every class with fewer than 3 groups in validation or test as "weak per-class evidence" (such a class behaves like one or two test vectors). The flag is informational and does not change the split.
- `scaler_minmax.json`: `sklearn.preprocessing.MinMaxScaler(feature_range=(0, 1), clip=False)` (both options pinned explicitly (rev 3); `clip=False` is required because `clip=True` would silently clip held-out inputs that fall outside the training range, contradicting the no-clipping policy in §E2; a test asserts `scaler.clip is False` and that a value above the training maximum transforms to a value above 1.0) fitted on the **training rows only** (`data_min_`, `data_max_`, `scale_`, feature names, hash of train IDs). Loading verifies the train-ID hash.
- `range_audit.json` and `split_report.md`, `split_attempts.json` (see read-only audit below).

**Sharing.** One split file and one scaler are loaded (never refit) by every variant and every seed. `load_arrays(split, scaler, partitions)` recomputes the hashes and asserts they match the frozen manifest.

**Assertions (in `make_split` and again in `load_arrays`):** partitions are disjoint and cover all 29,997 IDs exactly once; the set of group hashes of any two partitions is empty; every class appears in every partition; scaler `data_min_/data_max_` equal those recomputed from train rows; no constant training feature (else fail; audit says none).

**Read-only audits allowed on test:** ID/count integrity, class coverage, scaled input range, infeasible-row counts. These run on features and labels only. No model is constructed or called on test arrays.

**Out-of-range values.** MinMax is fitted on train, so held-out features can fall outside [0,1] (audit §5.4: a value of 2.0 in some splits). `range_audit.json` lists, per partition, count and row IDs of rows with any value outside [0,1] and their maximum excursion. Clean inputs are never clipped. Policy in §E.

**Framing sentence (required verbatim in every report):** "This is a new group-disjoint evaluation partition within a previously examined dataset, not a completely untouched external benchmark. The dataset was seen by Milestone 1; the earlier test partition was evaluated; identical feature vectors with conflicting labels remain in the data."

**No test inference in M2A.** Enforcement is layered (invariant owner in brackets):
- [`m2_split.load_arrays`] returns arrays only for `train`/`validation`. `purpose="range_audit"` is the only route to test features and returns scaled features to audit functions that take no model.
- [`m2_pilot`/`m2_campaign`] have `phase` in `{m2a, m2b_validation, m2b_test}`. `m2a` and `m2b_validation` reject any partition other than train/validation with `PartitionGuardError`. `m2b_test` additionally requires `--confirm-freeze <sha256 of configs/m2/campaign.json>` and is out of scope for M2A.
- [`evaluation.evaluate`] is not edited, but the M2 driver always passes `evaluation_partition="validation"`; a unit test asserts the driver raises for `"test"`.
- [test] `tests/test_m2_split.py::test_no_model_call_on_test` monkeypatches `torch.nn.Module.__call__` to fail while the audit functions run.

## B. Baseline training

**Decision B1: M2 baseline = Experiment C recipe on the new split.** Implemented by ONE training loop in `research/m2_training.py::train_unit(adversarial=False|True)` that reuses `paper_described_adam.build_optimizer/derived_seed/to_sequence/seed_everything` and reproduces `run_epochs` batching, shuffle, noise and optimizer-step logic. V1 and V3 both run through this single loop (AT off = V1), so pairing is structural. `run_epochs` has no hook between batch construction and the loss, so it cannot host AT. A regression test (`test_v1_matches_run_epochs`) trains a tiny model with `run_epochs` and with `train_unit(adversarial=False)` for 2 epochs and requires bit-identical final weights (`state_hash`). The loop also owns the divergence check: a non-finite loss raises `TrainingDivergedError` (§I). It is NOT `training.train` (that differs in scaler, batch, weight decay, clipping and checkpoint rule; audit §3).

Frozen values (`configs/m2/training.json`), inherited from C unless stated:

| Item | Value |
|---|---|
| Model | `common.make_model`, `StandardTransformerIDS(39, d_model 96, 4 heads, 3 layers, d_ff 384, 27 classes, max_seq_len 50, dropout 0.1)`, upstream pin `e73911bb...`, 351,612 parameters; asserted unchanged |
| Precision, device | FP32, CPU |
| Optimizer | `torch.optim.Adam`, lr 0.001, weight_decay 0.0001 (L2 in gradient), betas (0.9, 0.999), eps 1e-8; no schedule, no clipping; `build_optimizer` asserts class is `Adam` not `AdamW` |
| Loss | unweighted `F.cross_entropy` on `logits` |
| Batch | 512, `drop_last=False`, 25 epochs. Train partition ~22.4k rows gives ~44 steps per epoch, ~1,100 steps in total (exact count recorded; differs from C's 1,050 because the split differs) |
| Seeds | 1, 7, 13, 29 (eventual campaign); pilot uses seed 1 only |
| Checkpoint | final epoch only; validation used for reporting and attack-budget adequacy only, never for selection |
| Sequence | each MinMax-scaled row repeated 50 times to `(B,50,39)`. This is synthetic, not chronological traffic |
| Training noise | Gaussian std 0.01 added after repetition, independent per position, fresh each batch and epoch; evaluation is noise-free (inherited, documented) |
| Threads | `torch.set_num_threads(2)` for training (as C); 1 for efficiency timing |
| Determinism | like C, `torch.use_deterministic_algorithms` is NOT enabled for training. Run-to-run bit-exactness is not claimed; seeds make streams reproducible. The choice and torch/CPU versions are recorded in the run manifest |

The old M1 accuracy (about 64 % test, different split) is never used as a baseline or a comparison number. M2 reports its own FP32 baseline.

**Pairing and RNG isolation.**
- Initialisation: `seed_everything(seed)` then `make_model`, executed identically for the ordinary and AT models, so both start from the same initial weights for a given seed. A test compares `state_hash` at init.
- Shuffle order: `derived_seed("shuffle", seed, epoch)` (same for both variants).
- Training noise: `derived_seed("noise", seed, epoch, batch)`; the same noise tensor is added to the clean and the adversarial sequences of a step (§D).
- Attack generation uses only `seed=derived_seed("atk-train", seed, epoch, batch)`, passed as the integer `seed` argument of `attacks.attack` (the engine builds its own local `torch.Generator` from it and uses it for all restarts). It never touches the global RNG, shuffle or noise streams. The attack runs in `eval()` mode, so it does not consume dropout draws. A test trains an ordinary model for one epoch with and without an interleaved attack call and asserts identical weights.
- Not pairable: dropout masks. The AT step performs two train-mode forward passes (clean and adversarial) per update, so global-RNG dropout draws diverge from the ordinary run after step 1. This is documented as an unavoidable difference and not corrected.
- Budget: identical epochs, batch size, shuffle order, optimizer and number of optimizer updates. AT extra compute is reported (§D).

## D. Adversarial training

**Decision D1 (frozen in `configs/m2/training.json["adversarial"]`):**

| Item | Value |
|---|---|
| Space | MinMax-scaled feature space, L-infinity |
| Training epsilon | 0.05 (the middle of the evaluation grid). Chosen a priori, not tuned. One value, no curriculum |
| Attack | untargeted cross-entropy PGD, 5 steps, step size 0.025 (= eps/2), uniform random start in the feasible box, 1 restart, executed by the existing `attacks.attack(kind="pgd", steps=5, alpha=0.025, restarts=1, random_start=True)`. Retention is that function's strongest-candidate rule over {FGSM candidate, random start, each iterate}: a misclassified candidate beats a correct one, ties broken by higher CE. The FGSM candidate IS included in training attacks. No final-iterate mode is added; `attacks.py` gets only the `selector` keyword. The training adversary is therefore at least as strong as a final-iterate PGD-5; this is disclosed |
| Perturbation structure | row-tied (§E1): one 39-d delta broadcast to all 50 positions |
| Loss | `0.5 * CE(clean) + 0.5 * CE(adv)`, both on `logits`, original labels |
| Model mode during attack | `eval()` (dropout off) and restored to `train()` afterwards; modes of every submodule recorded and restored |
| Attacked model | the current model weights at that step |
| Initialisation | fresh, same seed init as V1 (not fine-tuned from V1) |
| Optimizer, schedule, batch, epochs, shuffle | identical to B1, same `train_unit` loop |

**Mechanics per step.** (1) `x_row` batch (B,39) from the shuffled order. (2) Switch to eval, generate `x_adv_row` through `RowTiedModel` and `attacks.attack` (which computes `torch.autograd.grad` with respect to the input only and restores per-module modes), with the integer `seed` argument (local generator built inside the engine); no parameter `.grad` is written. (3) Restore train mode. (4) Build noise `eps_noise` once from `derived_seed("noise", ...)` and form `seq_clean = repeat(x_row)+noise`, `seq_adv = repeat(x_adv_row)+noise`. (5) One forward on each, combine the loss, `opt.zero_grad`, backward, `opt.step`. The attack sees the noise-free sequence; training adds the same noise to both, so the perturbation is not "washed out" differently from the clean pass, and the repeated sequence stays an exact repetition of one perturbed row before noise. Per-position independent noise is inherited and not adversarial.

**Safeguards (asserted in code and tests).** Before/after the attack call: parameter `state_hash` is unchanged; all `p.grad` are `None` or unchanged (compared with a snapshot); `x_adv_row` finite and `|x_adv-x|_inf <= eps + 2e-6` (the engine tolerance, see §E5) and inside the feasible set (§E2); module modes restored. Violation raises `AttackInvariantError` (fatal for the run unit, logged at ERROR with the step index). `m2_attacks.checked_attack` also catches the `FloatingPointError` raised by `attacks.attack` (non-finite input, logits or gradients) and re-raises it as `AttackInvariantError` carrying the check name (`finite_inputs`, `finite_logits` or `finite_gradients`) with the original exception chained. (rev 3) It also catches the `AssertionError("Attack budget or finiteness violation")` that the engine raises at its final check (`best` non-finite or `|best - x|_inf > epsilon + 2e-6`) and re-raises it as `AttackInvariantError("linf_budget")`, original chained. The engine's single assertion covers both a budget and a finiteness violation, so `checked_attack` re-checks finiteness of the returned tensor itself before choosing the name: non-finite output is reported as `finite_inputs`, otherwise `linf_budget`. A test patches the engine to raise `AssertionError` and asserts the mapped class and name. `python -O` strips `assert` statements but the engine uses an explicit `raise`, so the check survives optimised mode.

**Compute accounting (rev 3)** (`train_log.json`): wall-clock seconds, optimizer updates (must equal V1's), and three per-step counters derived from the actual `attacks.attack(kind="pgd", steps=5, restarts=1, random_start=True)` control flow: `attack_grad_passes_per_step = 6` (1 gradient at the clean point for the FGSM candidate, then 5 PGD iterations; each is a forward plus an input-only backward), `attack_scoring_forwards_per_step = 8` (forward-only `consider()` and baseline scoring: clean baseline, FGSM point, random start, 5 iterates), and `train_forward_backward_per_step = 2` (clean and adversarial; V1 has 1). Ordinary V1 logs `0 / 0 / 1`. `train_unit` logs these from the frozen attack configuration, and a test confirms them empirically on a tiny model: a forward hook on the model counts 14 attack-side forward calls per step (6 gradient forwards, each followed by an input-only backward, plus 8 scoring forwards) and 2 training forward/backward calls, and the test asserts the logged constants 6, 8 and 2 match. The same hook count is repeated once in the pilot on the real model (first step only) and stored in `train_log.json`, so the constants cannot drift from the engine unnoticed. This relies on the pre-edit `attacks.attack` calling `logits(model, ...)` once per scoring or gradient point, which is why the `selector` edit (§J) is specified to leave the call structure unchanged. The reported extra-cost figure has two parts, both shown: (a) the nominal pass-count ratio `(2*3 + 6*3 + 8*1) / 3`, using the stated assumption that a forward costs 1 unit and a forward+backward costs 3 (so 32/3 ≈ 10.7; the input-only backward is somewhat cheaper than a full weight backward, so this is an upper-leaning estimate), and (b) the measured wall-clock ratio of AT to ordinary. The wall-clock ratio is the headline number; the nominal ratio is the cross-check. Both are reported with the raw per-step list. Pilot measurement of this ratio feeds the campaign estimate. The earlier pilot saw 6.6x with a 3-step attack plus FGSM (audit §6). A 2-epoch pilot has only about 12 updates, so the pilot ratio is indicative only: it is computed from per-step times after discarding the first step of each run (warm-up and allocation noise) and reported with the raw per-step list.

## E. Adversarial evaluation protocol

**Frozen epsilon grid:** `[0, 0.01, 0.025, 0.05, 0.10]` in MinMax-scaled feature space (a fraction of each feature's training range; not comparable with the earlier standard-deviation-unit epsilons). Reports state: "feature-space attacks; no guarantee that perturbed vectors correspond to valid network traffic."

**E1. Perturbation structure: row-tied (primary).** The adversary controls one 39-d delta per example, broadcast to the 50 identical positions. Rationale: the sequence is a synthetic repetition of one feature row, so per-position freedom (50x39 variables) would be an attack on an input that no real feature row represents. Implementation: `RowTiedModel(nn.Module)` takes `(B,39)`, calls `to_sequence` (repeat), and returns `{"logits": self.model(to_sequence(x))["logits"]}`, because `attacks.logits` does `model(x)["logits"]`. The `bpda_model` wrapper is wrapped the same way (`RowTiedModel(bpda_model(...))`). Tests: `attacks.attack` runs end to end through `RowTiedModel`, and a `bpda_model` inside `RowTiedModel` keeps `atol=0` forward agreement with the real INT8 model. `attacks.attack`, `bpda_model` and `evaluation` operate on `(B,39)` through this wrapper; no change to the attack engine's mathematics. The inherited per-position mode (M1 C, `attacks.attack` on `(B,50,39)`) is kept only as a labelled sensitivity check on seed 1 / validation; it is never mixed into headline tables.

**E2. Feasible set and out-of-range policy (one policy for the whole grid).** For clean value `x` and `eps >= 0`:
`lower = max(x - eps, min(0, x))`, `upper = min(x + eps, max(1, x))`.
This is `attacks.attack` called with tensor bounds `lower=torch.zeros_like(x), upper=torch.ones_like(x)` (the code evaluates `torch.minimum(lower, x)`, so Python floats are rejected; a test covers this) (audit §4.2, §7). Consequences: the interval always contains `x` (never empty); `eps=0` returns `x` exactly; clean inputs are never clipped, dropped or skipped; epsilon is never enlarged; an out-of-range coordinate (e.g. 2.0) can only move toward the interior within `[x-eps, x]`, which is a conservative restriction for that coordinate and is disclosed. `adversarial_domain.feasible_bounds` (raises `InfeasibleConstraintError`) is NOT used. The report states the count of validation rows with any out-of-range coordinate, and per-epsilon the count of coordinates whose interval is one-sided; no row is excluded. Unit tests cover x=2.0, x=-0.3, x=0.5, eps in the grid.

**E3. Attack definitions (untargeted, CE loss, original labels retained, model in `eval()`).**
- **FGSM (rev 3):** one step `x + eps*sign(grad)` clamped to the feasible set. Decision: the protocol uses `attacks.attack(kind="fgsm")` unchanged and no fgsm-only early path is added to the planned `selector` edit (smaller diff to M1 code, and the retained point is identical either way). With `kind="fgsm"` the engine sets `nsteps=1, nr=1, alpha=epsilon` and scores **3 candidates**: (1) the initial FGSM point; (2) inside the restart loop, an unperturbed copy `x.clone()` (FGSM has no random start); (3) the point after one gradient step from that copy, `clamp(x + alpha*sign(g))` with `alpha = eps` and `g` the gradient at `x`, which is bit-identical to candidate 1. The selector is called **4 times per batch** (clean baseline plus the 3 candidates). Candidate 2 can never replace the baseline (the baseline already scores `x`, and `take` needs a strictly higher CE or a new success), and candidate 3 duplicates candidate 1 and cannot replace it (strict `>`), so the retained point is the FGSM point or `x`. The duplication costs two extra target forwards per batch and is accepted and disclosed rather than fixed. The FGSM gradient is also computed twice per batch (2 gradient passes). Expected counts: `n_selector_calls = 4 x n_batches`, `candidates_scored_on_target = 3 x n_batches`.
- **PGD (frozen evaluation budget "pgd20", provisional until E4 is re-run on fully trained checkpoints):** 20 steps, step size `alpha = eps/4`, uniform random start inside the feasible box, `restarts=3`, L-infinity projection to the feasible set each step. In `attacks.attack`, `restarts=3` means three independent random-start PGD runs of 20 steps each, plus the single FGSM candidate evaluated first; there is no separate clean-start run. Candidate set per example: FGSM point, each random start, and every iterate of every restart (1 + 3 x (1 + 20) = 64 candidates; selector calls per batch = 1 baseline + 64 = 65). At `epsilon == 0` the engine returns `x.clone()` before any scoring: 0 candidates and 0 selector calls (see E5). **Retention rule (the `attacks.attack` code):** every candidate is scored on the target; a misclassified candidate replaces a correctly classified retained one, and between two candidates in the same success state the higher cross-entropy wins (`take = (wrong & ~best_wrong) | ((wrong == best_wrong) & (loss > best_loss))`). So a later successful candidate with higher CE can replace an earlier successful one, but a successful candidate is never replaced by an unsuccessful one. Robust accuracy = fraction correct on the retained candidate. Final-iterate accuracy and loss-versus-iteration traces are NOT outputs of `attack()` and are not reported.
- **Seeds:** for example batch `b`, eps `e`, model id `m`, source label `src`, training seed `s`, the call is `attacks.attack(..., seed=derived_seed("atk-eval", s, m, src, e, b))`. The engine builds one local `torch.Generator` from this integer for all restarts, so no global RNG is touched. Evaluation batch size 64.
- **Evaluation partition for M2A and for budget adequacy:** validation only.

**E4. Budget adequacy (validation only, frozen decision rule; `pgd20` is PROVISIONAL).** Reference budget "pgd50x5": 50 steps, alpha = eps/10, `restarts=5`. Rule, run on seed-1 fully trained checkpoints of **V1 (`fp32_direct`), V2 (`bpda_int8`), V3 (`fp32_direct`) and V4 (`bpda_int8`)** at eps 0.025, 0.05 and 0.10, on a fixed validation attack subset (rev 3): **all validation rows if the validation partition has `n <= 2,500` rows, otherwise the subset returned by `data.stratified_cap(val_ids, val_labels, e4_per_class_cap, derived_seed("e4-subset", <frozen split seed>))`**, with the frozen constant **`e4_per_class_cap = 70`** stored in `attacks.json`. `stratified_cap` draws `min(70, class count)` rows per class, so the subset has at most 27 x 70 = 1,890 rows; its exact size `n_subset` is whatever the function returns for the frozen split and is recorded (with the per-class counts) in `attack_budget_check.json`, not asserted in advance. If `n_subset < 1,000` the E4 step stops and asks the user (it never lowers the threshold, changes the cap or substitutes rows on its own). The ID list and its hash are saved and reused for all four models. The comparison is paired per example: for each (model, eps) cell let `n_extra` = number of examples that pgd50x5 breaks (retained candidate misclassified) but pgd20 does not. pgd20 is adequate if **`n_extra <= ceil(0.01 * n_subset)`** in every one of the 12 cells (equivalently at most 1.0 % of the subset, rounded up to a whole example). (A paired count is used because a 1-point margin on unpaired accuracies is below sampling noise.) If any cell fails, the campaign uses pgd50x5 for every model, source and epsilon (one rule, no model-specific budgets). The BPDA cells use the INT8-target selector, so approximate-backward budget needs are covered. Result goes to `attack_budget_check.json` with all 12 `n_extra` values. The budget is never tuned toward a target accuracy or against published Table 4.
Where it runs: the M2A pilot trains for only 2 epochs on a small subset, so the pilot run of E4 is a plumbing check on the 270-row pilot attack subset (code path and cost measurement) and establishes nothing about adequacy. `attacks.json` therefore marks `pgd20` as `"status": "provisional"`. The decisive run is a **named, blocking first step of the campaign plan (step 0 in §H)**: train seed-1 V1 and V3 fully (25 epochs, which the campaign requires anyway), derive V2 and V4, run E4 on the validation partition, freeze the budget in `attacks.json` (status `"frozen"`, hash written into `campaign.json`), and only then continue with the remaining seeds and attacks. M2A does not run it because that would exceed the bounded-pilot limit (one seed, at most two epochs).

**E5. Required checks on every attack run (`attack_checks.json`; any failure invalidates the unit):** inputs finite; logits finite; gradients finite; `|x_adv - x|_inf <= eps + 2e-6` (one tolerance everywhere, equal to the `attacks.attack` engine tolerance; in float32, `x + eps` at x = 2.0 rounds with error up to about 1.2e-7, so a tighter wrapper bound could reject valid output; a test with x=2.0, eps=0.01 asserts no false failure); `x_adv` inside the feasible set (E2); model not training-mode during attack and mode restored; parameters unchanged (`state_hash` before = after); no `.grad` on parameters; labels equal to the stored labels (hash compared); eps=0 gives predictions identical to clean predictions for every source/target pair (index-by-index); clean and attacked results use the same example IDs, labels and checkpoint (hashes recorded in each result row). **Fields recorded in `attack_checks.json` (per unit: model id, source, attack, eps):** `selector_target_id` (id and `state_hash` of the model that scored every candidate: the actual INT8 model for every INT8 target row, the FP32 model for `fp32_direct`), `candidates_scored_on_target` (rev 3: counted in batch-level selector calls, and must equal the per-batch candidate count in E3 times `n_batches`: 64 x n_batches for pgd20, 3 x n_batches for FGSM, 0 at epsilon 0), `n_selector_calls` (65 x n_batches, 4 x n_batches, 0 respectively), `bpda_forward_max_abs_err` (maximum absolute difference between the BPDA wrapper logits and the real INT8 model logits over the WHOLE evaluated set, including every candidate the attack scored; the unit fails if it is not exactly 0.0; recorded as `null` at epsilon 0 because no candidate is scored), plus the boolean result of each check above and the example-ID hash.
**Mechanism for the target-side checks: `m2_attacks.CheckedPair(bpda_model, int8_model)`.** Its `__call__(x)` is the `selector` passed to `attacks.attack`. It (a) computes `a = int8_model(x)` and returns `a` (candidates are scored by the real INT8 model), (b) under `torch.no_grad()` also computes `b = bpda_model(x)` on the same input and updates `max_abs_err = max(max_abs_err, (a - b).abs().max())`, and (c) increments `n_selector_calls`. The selector is called for the clean baseline and for every candidate, so the forward comparison covers every scored candidate and not only gradient points. Expected count per attack batch (rev 3, verified against the `attacks.attack` control flow) is `1 + n_candidates`: for pgd20 with 3 restarts `1 + 64 = 65` calls; for FGSM `1 + 3 = 4` calls, because the engine scores the FGSM point, an unperturbed copy and a repeated one-step point (E3). The unit requires, for epsilon > 0, `n_selector_calls == 65 x n_batches` (pgd20) or `4 x n_batches` (FGSM); `candidates_scored_on_target` is recorded as `n_selector_calls - n_batches` and checked against `64 x n_batches` (pgd20) or `3 x n_batches` (FGSM). The unit fails unless `max_abs_err == 0.0`. The expected-count table is keyed by `(attack kind, restarts)` and is read from `attacks.json`, not hard-coded in the check.
**Epsilon 0 (rev 3).** `attacks.attack` returns `x.clone()` before any scoring, so at epsilon 0 the selector is called 0 times and the count rule above does not apply: expected `n_selector_calls = 0`, `candidates_scored_on_target = 0`, `bpda_forward_max_abs_err = null` (never 0.0, so an unset value cannot masquerade as a pass). The eps=0 unit is validated by the clean-prediction identity check instead: `x_adv` must equal `x` bitwise, and the target predictions on `x_adv` must equal the clean predictions index by index. The clean predictions, for every epsilon, come from one explicit `selector(x)` call per batch made OUTSIDE `attack()` (for BPDA rows through the same `CheckedPair`, whose clean-baseline calls are tallied in a separate counter `n_clean_calls = n_batches` and do not enter `n_selector_calls`; the clean-call logits are still compared with the BPDA wrapper and any non-zero difference still fails the unit, but at epsilon 0 the recorded field remains `null` because no attack candidate was scored). Sources with `selector=None` use the target model directly for the clean call. For INT8 rows without BPDA (`transfer_*`, `surrogate_*` target-selected) a plain counting selector with the same expected counts is used and no BPDA comparison is made. Pure `transfer` and pure `surrogate` rows make exactly one target evaluation per example after attack construction. For `fp32_direct`, `selector=None` and the count check is skipped.

**E6. INT8 attack taxonomy (results never merged across sources).** Each row in `attack_results.csv` carries `attack_source`, `target`, `attack`, `eps`:

| Source label | Gradient from | Evaluated on | Notes |
|---|---|---|---|
| `fp32_direct` | FP32 model | same FP32 model | white-box FP32 (V1, V3) |
| `transfer_fp32_to_int8` (PURE transfer) | FP32 parent (V1->V2, V3->V4) | `selector=None`: the FP32 parent ranks and retains candidates; the retained `x_adv` is then evaluated exactly once on the actual INT8 target | no query to the INT8 model during attack construction; this is the only row called "transfer" |
| `transfer_fp32_to_int8_targetsel` | FP32 parent | actual INT8 target, which also selects among candidates (`selector` = INT8 model) | labelled "gradient from FP32, candidate choice by INT8 target queries"; stronger than pure transfer, not a transfer attack |
| `bpda_int8` | actual INT8 target forward, backward through dequantized weights (`quantization.bpda_model`) | same INT8 model; `selector` = `CheckedPair` (E5) | forward agreement with the real INT8 target asserted at exactly 0.0 on every scored candidate; the approximate backward pass is disclosed in every table |
| `surrogate_fakequant` (pure) | fake-quant surrogate of the parent (construction below) | `selector=None` (surrogate retains candidates), retained `x_adv` evaluated once on the actual INT8 target | secondary diagnostic; the surrogate is a different function than the deployed model |
| `surrogate_fakequant_targetsel` | same surrogate | actual INT8 target selects candidates | labelled as query-assisted |
| `direct_int8_grad` (diagnostic only) | autograd through the converted modules | n/a | Autograd through converted `quantized::linear` normally raises `RuntimeError` (no `grad_fn`) rather than returning zeros. The diagnostic catches `RuntimeError`, counts the batch as undefined-gradient fraction 1.0, and also counts all-zero or non-finite gradients when nothing raises. The slow test on the real converted model records which behaviour occurs. Never reported as robustness |

**Surrogate construction (`m2_attacks.build_surrogate(parent, calibration_ids)`).** (1) `quantization.prepare_static(copy_of_parent, "all_linear", example, qat=True)`: same 23 islands, fbgemm qconfig family as PTQ. (2) (rev 3) `prepare_static(qat=True)` calls `converted.train()` before `prepare_qat`, and a train-mode forward would switch dropout (p=0.1) on, making observer statistics random, dependent on the global RNG and different from the PTQ calibration pass (which runs in `eval()`). So, immediately after `prepare_static` returns: `model.eval()`, then `torch.ao.quantization.enable_observer(model)` and `torch.ao.quantization.enable_fake_quant(model)` (observers and fake-quant are governed by their own enable flags, not by `model.training`, so they stay active in eval mode), then run the same 540 calibration rows (the saved PTQ ID list, noise-free repeated sequences, same row-tied adapter) in batches of 32 under `torch.no_grad()`, in the saved ID order. (3) Apply `torch.ao.quantization.disable_observer(model)` (fake-quant stays enabled so the surrogate quantizes in forward) and leave the model in `eval()`. (4) Weights are exactly the parent's; no fine-tuning. **Determinism test (rev 3):** building the surrogate twice from the same parent and calibration IDs gives identical per-island `scale` and `zero_point` tensors (exact equality), and the build consumes zero dropout draws: a forward pre-hook on every `nn.Dropout` asserts `module.training is False` on every calibration batch, and the global RNG state (`torch.get_rng_state()` hash) is identical before and after the build. Gradients pass through fake-quant with the straight-through estimator. Fidelity is logged as `max |scale_surrogate - scale_int8|` and `max |zero_point difference|` per island plus the maximum logit difference to the real INT8 model on the attack subset. If any scale differs, every table row from this source carries the note "surrogate scales differ from deployed INT8 scales (max diff = ...)". The QAT qconfig uses moving-average observers, so differences are expected and are reported, not hidden.

Rules: (i) a missing, zero or NaN gradient through quantized operators is recorded as a gradient-masking diagnostic (per-example undefined-or-zero-gradient fraction on the **full** evaluated set, replacing the existing 2-example probe) and never counted as robust; (ii) the headline INT8 robustness is the `bpda_int8` result; the `transfer` and `surrogate` rows (pure and `_targetsel`) are supporting evidence; a per-example union ("any source succeeded") is reported as a separately labelled row; (iii) the INT8 robust accuracy is only ever computed from INT8 logits of the retained candidates (every candidate is evaluated on the actual INT8 model); (iv) AT->INT8 and FP32->AT-INT8 cross transfers are optional extras in the campaign, not required in the pilot.

## F. Efficiency protocol (`research/m2_efficiency.py`)

- **Artifact size:** bytes of the serialized *inference* artifact (`state_dict` only: no optimizer, no calibration tensors, no logs) for V1-V4, plus the number of quantized vs FP32 parameters.
- **Conditions:** the same machine, `torch.set_num_threads(1)` (primary) and 4 (secondary, full campaign only), `OMP/MKL` threads matched, fbgemm engine, models in `eval()` under `torch.inference_mode()`, one fixed list of 256 validation row IDs (saved with hash) for all models, no other heavy process running (checked: pre-run CPU load recorded).
- **Latency/throughput:** batch size 1 (`warmup 20`, `timed 200`; pilot 10/50) and one fixed throughput batch of 256 (`warmup 5`, `timed 30`; pilot 2/10). Report median, p95, min and the raw samples; throughput = samples per second from the median batch time. Repeat each model in `3` independent processes and report the spread. (rev 3) The order is interleaved across repetitions, not model-by-model, so that thermal drift on the laptop CPU is spread over all models instead of confounding one: repetition 1 runs V1, V2, V3, V4, repetition 2 runs V1, V2, V3, V4, repetition 3 runs V1, V2, V3, V4 (12 processes in the order V1,V2,V3,V4,V1,V2,V3,V4,V1,V2,V3,V4). The executed order, a start timestamp per process and the pre-run CPU load are recorded in `efficiency.json` (`run_order`). Any retried process (§I) is appended at the end and flagged, and the order is never re-sorted. The pilot uses the same interleaving with its reduced repetition count.
- **Scope of the timed region:** input row tensor -> repeat to 50 positions -> model forward -> argmax. Excluded: CSV reading, MinMax scaling (it is a trivial fixed affine op, identical for all models; stated), attack generation, calibration, model loading.
- **Memory:** each model is measured in its own fresh subprocess (`py -B -m research.m2_efficiency --child ...`). Baseline = process RSS after imports and model/checkpoint load and before the first inference; peak = `psutil.Process().memory_info().peak_wset` (Windows peak working set) after the timed runs, cross-checked by a 10 ms sampling thread (`provenance.MemoryMonitor`). Report both and `peak - baseline`. Process-wide RSS is coarse and includes allocator slack; this is stated.
- **Mixed-precision coverage:** from `conversion.json`: number and share of parameters in INT8 Linear islands, number of FP32 modules/ops (§C list), and the count of quant/dequant boundaries. No claim that INT8 is faster or smaller in memory; the audit pilot found INT8 slower at batch 1 on this CPU (20.5 vs 14.0 ms). Outcomes are reported as measured with their spread.

**Modified (minimal):** `research/attacks.py`: one optional keyword `selector=None`. Signature: `selector: Callable[[Tensor], Tensor] | None`, taking an input batch `(B,39)` and returning target logits `(B,27)` (finite-checked like `logits()`). When given, `selector` replaces `logits(model, .)` in exactly two places: the initial baseline (`original`, `best_loss`, `best_wrong`, computed on clean `x`) and every `consider(candidate)` call, so candidate ranking and success are always judged on the target. The gradient step (`gradient()`) always uses `model` (the source: FP32 parent, BPDA wrapper or fake-quant surrogate). The `epsilon == 0` early return is unchanged (returns `x.clone()` before any scoring), so eps=0 predictions equal clean predictions on every source/target pair. `selector=None` behaves exactly as today and is covered by the existing attack tests. Required test: a stub target whose argmax differs from the source model confirms that retained candidates are chosen by the stub and that the baseline uses the stub. Selector per source: `bpda_int8` uses `CheckedPair(bpda, int8)` (row-tied); `transfer_fp32_to_int8_targetsel` and `surrogate_fakequant_targetsel` use the real INT8 model; pure `transfer_fp32_to_int8`, pure `surrogate_fakequant` and `fp32_direct` use `None` (the source model ranks candidates; the pure rows then evaluate the retained `x_adv` once on the INT8 target). The edit does not change the call structure (rev 3): FGSM still scores 3 candidates with 4 selector calls per batch and PGD (3 restarts, 20 steps) 64 candidates with 65 calls, because §E5 and §D's compute counters depend on those numbers; no fgsm-only early path is added. Nothing else in M1 code is edited.
**Never modified:** the protected paths listed in §G.

**Testability.** Unit-testable on tiny models and synthetic tables: the split algorithm, guard, feasible policy, row-tied tie, retention logic, RNG isolation, loss weighting, config validation, integrity script, conversion verification. Integration-tested on the real model and data (marked slow, run in the pilot): parameter count and upstream pin, 23-island conversion, reload equality, BPDA exactness, efficiency subprocess measurement, QAT conversion.

## K. Assumptions and known unknowns

- The 74.8/12.6/12.6 split figure is exploratory; the real achieved counts come only from running `m2_split` with seed 20260. If the acceptance band is missed the work stops for a user decision.
- Training epsilon 0.05, 5 steps and the pgd20 budget are a priori choices; only the E4 rule (pre-declared) can raise the evaluation budget.
- Dropout streams cannot be paired between V1 and V3.
- INT8 may be slower than FP32 on this AVX2-only CPU; no speed or memory claim is assumed.
- The pilot's two epochs give a nearly untrained model; attack-budget adequacy on such a model is only a plumbing check. E4 is formally re-run on fully trained seed-1 checkpoints at the start of the full campaign (validation) before the budget is frozen for test.
- Pilot E4 is a plumbing check only; adequacy is decided in campaign step 0 (E4).
- (rev 3) The E4 subset size is not known until the frozen split exists; it is at most 27 x 70 = 1,890 rows when the validation partition has more than 2,500 rows. The expected selector-call table (pgd20 65/64, FGSM 4/3, epsilon 0 0/0) was read from the current `attacks.attack` control flow and is guarded by tests; if `attacks.py` changes, the table and the tests must change together.
- (rev 3) The nominal AT pass-count ratio (about 10.7x) assumes backward = 2 x forward and is a cross-check only; the wall-clock ratio is the reported cost.
